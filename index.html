Abstract

This project builds a semantic image search engine over a personal photography archive of 83 images. Using CLIP (Contrastive Language–Image Pre-training), each image is embedded once into a 512-dimensional vector space that is shared with natural language. At query time, a text prompt is embedded into the same space and cosine similarity is computed against every image embedding, returning the top-k most similar images in a Gradio interface. No captioning or text generation is involved — the system is pure retrieval.

The central finding is that CLIP's retrieval quality on personal photography is meaningfully lower than on internet imagery, and that the gap is not random: it is structured by the mismatch between CLIP's training distribution (captioned web images) and the visual characteristics of personal archives (unconventional angles, personal context, absence of stock-photo composition). Documenting and mechanistically explaining this mismatch is the core contribution of this write-up.

Approach

The pipeline has four stages: image loading, embedding, indexing, and retrieval. CLIP is used as a joint text–image embedding model — both modalities are projected into the same 512-dimensional space, making direct comparison possible without any intermediate captioning or generation step.

Model choice

I used openai/clip-vit-base-patch32 — the smallest standard CLIP checkpoint. This divides each image into non-overlapping 32×32 pixel patches which are processed by a Vision Transformer (ViT). A larger model (clip-vit-large-patch14) uses finer 14×14 patches and produces better representations, but the base model is sufficient to demonstrate the pipeline and produces more interesting failure cases for analysis.

Similarity and parameters

Because all vectors are L2-normalised to unit length, the dot product between any two vectors equals the cosine of the angle between them — a score of 1.0 means identical direction (perfect semantic match) and 0.0 means orthogonal (unrelated). I settled on a threshold of 0.20 after experimentation: scores above ~0.28 reliably correspond to strong visual matches in this corpus, while scores below 0.20 are usually coincidental overlaps. Top-K was set to 6 for the interface and varied during atlas construction.

Key implementation note

The version of the transformers library available on Colab wraps model outputs in a BaseModelOutputWithPooling object rather than returning a raw tensor. Both get_image_features() and get_text_features() required an extra .pooler_output extraction step before normalisation. This is worth noting for reproducibility. 

# The fix required for transformers >= 4.x on Colab
features = model.get_image_features(**inputs)
if hasattr(features, 'pooler_output'):
    features = features.pooler_output
features = features / features.norm(dim=-1, keepdim=True)

Limitations

Limitation Why it happens Possible fix
Low similarity scores across corpus (~0.20–0.30) CLIP was trained on internet imagery; personal photos deviate from that distribution Fine-tune CLIP on personal data, or use a larger model variant
No semantic understanding of personal context CLIP sees visual features, not meaning — it cannot know "my dog" vs "a dog" Add captions or metadata as a secondary retrieval signal (Level 2)
Scores collapse for abstract queries Words like "memory" or "nostalgia" have weak visual correlates in the embedding space Prompt engineering — describe the visual appearance instead of the concept
Embeddings stored in RAM, not a vector database Simple numpy matrix multiplication — does not scale beyond a few thousand images Replace with FAISS or similar for larger corpora
Session-persistent only — re-upload required on Colab restart Colab's free tier does not persist files across sessions Store embeddings and images on Google Drive or an external host
